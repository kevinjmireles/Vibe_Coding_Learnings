# Repository Instructions Evolution: From Prompt Notes to Engineering Handbook

## Early approach

Project instructions began as guidance for getting an AI to make useful changes. As new failures appeared, more rules were added.

## What the file became

The repository instruction file gradually evolved into a compact engineering handbook covering:

- product and architecture orientation;
- simplicity and scope rules;
- issue creation and acceptance criteria;
- Builder, Reviewer, and Steward responsibilities;
- anti-duplication checks;
- testing and evidence requirements;
- documentation expectations;
- security and operational safeguards;
- accessibility, localization, and scalability principles;
- session continuity and context management.

The important change was not merely adding more instructions. It was turning repeated failures into durable rules that every future agent would read.

## Why this is better

A model no longer needs the human to remember and restate every lesson. The repository carries those lessons forward across tools, conversations, devices, and contributors.

## Caution

An instruction file can become bloated or contradictory. Stable rules should point to canonical supporting documents rather than reproducing every detail. The goal is a reliable entry point, not a second copy of the entire repository.

## Reusable takeaway

**Every recurring failure deserves a rule, but every rule needs one canonical home.**
