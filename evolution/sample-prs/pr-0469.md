## Original PR description

> ## Summary
>
> Follow-up to #468. That PR's review surfaced lessons that go beyond one bug — this formalizes them as a standard for every future dataset's freshness policy.
>
> - **New "Series Freshness Contract" section** in `docs/architecture/token-catalog-vnext.md` (extended in place — this file is already the canonical SSOT for freshness vocabulary, so a new standalone doc would have duplicated it). Required fields: series/provider/dataset identifier, expected cadence, expected publication lag vs. observed end-to-end data lag (**upper bound**, not average — and these two are not interchangeable: publication lag is only measurable if `source_published_at` is actually captured, which most Fido pipelines don't do today), threshold + buffer rationale, date field + comparison semantics, named code constant, DB-side implementation, subscriber-facing fallback copy, and a `provisional` / `validated` status.
> - **Provisional-threshold policy:** a series may ship before 4+ ingest cycles of history exist, but must be marked `provisional` with a conservative threshold and revisited after 4-8 cycles. Codifies "two observations is not a distribution" — the exact gap that let #468's threshold (set from 2 weeks of logs) go unnoticed until it failed on week 3.
> - **Required 3-part test pattern** for any freshness threshold: (1) incident regression, (2) boundary (exactly-at / one-day-past), (3) neighbor isolation (changing one series' threshold doesn't silently change a sibling's — the test that would have caught #468's shared-constant bug immediately).
> - **Extracted `isDateOlderThanCalendarDaysUtc()`** (`src/lib/date/freshness.ts`, unit-tested) as a named, shared calendar-day comparison primitive. `isSnapshotStale()` in `tokens.ts` now delegates to it instead of inlining the same logic. Validates strict `YYYY-MM-DD` shape and round-trips the parsed UTC year/month/day, so an impossible calendar date (e.g. `2026-02-31`, which `new Date()` silently rolls forward to March 3) fails closed as stale rather than being silently accepted.
> - **Fixed a doc-drift bug:** the "Staleness thresholds" table was left stale by #468 — still showed one combined 14-day DOL claims row after the code split into state (42-day) / national (21-day). Now matches the actual constants.
> - **Deliberately not done:** `isPeriodStale()` still does elapsed-millisecond comparison, not calendar-day. Migrating it touches 5+ call sites with their own regression risk — documented as a follow-up, not attempted in this change.
> - **Also not done:** separating *data age* from *pipeline health*. Documented as a known gap; it would require additional timestamps tracked per row.
>
> ## Review round 2 fix — publication lag ≠ data lag
>
> The first draft of this PR called the 26-day figure from GitHub Actions ingest logs a "publication lag." That's incorrect: ingest logs only prove `ingested_at - data_period_end` (**observed end-to-end data lag**) — they say nothing about `source_published_at - data_period_end` (**publication lag**) unless the source's actual publish timestamp is separately captured. Corrected throughout.
>

## What this shows

By PR #469, the process had changed substantially:

- a defect from one PR became a reusable contract for future work;
- the existing canonical document was extended instead of creating a duplicate document;
- what was deliberately excluded was as explicit as what was implemented;
- review rounds corrected terminology and strengthened validation;
- test evidence included exact counts and boundary cases;
- failure behavior was fail-closed;
- rollback and risk were documented;
- documentation updates were tiered and checked;
- Builder and Reviewer grades were recorded.

The most important evolution is that review no longer ended with fixing one bug. The team asked what recurring failure pattern the bug revealed and then changed the system so future implementations would inherit the lesson.
