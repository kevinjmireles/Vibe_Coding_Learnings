## Original PR description

> ## Problem
>
> No canonical UI convention existed anywhere in the codebase. Rather than write a design-system document from opinion, this PR sequences the work as: audit what exists (evidence only) → analyze the gaps (judgment) → draft a canonical standard, so the standard is grounded in what is actually in the codebase instead of accidentally freezing today's implementation as tomorrow's rule.
>

>

> - `docs/architecture/design-system.md` — canonical UI conventions document, marked **DRAFT** where sections still needed revision.
> - Documentation index and registry updates.
>
> ### Excluded

> - No promotion of the design-system document out of draft; that work was tracked separately.

## What this shows

This example demonstrates a later-stage process that does more than validate code:

- evidence gathering is separated from interpretation;
- the audit precedes refactoring or standardization;
- actual bugs discovered during research are separated into their own issues;
- exclusions prevent a documentation PR from becoming an uncontrolled code change;
- architecture, internationalization, and knowledge-stewardship checks are explicit even when they are not applicable;
- the Builder handoff records implementation, deferrals, reuse, parallel paths, files, tests, limitations, and follow-ups;
- the self-grade honestly reflects known gaps rather than automatically claiming success.

It also demonstrates an important point: the workflow is useful even when a PR does not merge. The PR preserves evidence, decisions, gaps, and follow-up work. A closed PR can still contribute to institutional learning when the reasoning is documented.
